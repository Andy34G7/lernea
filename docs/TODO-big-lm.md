# Big proxy LM: open items

Branch `feat/big-proxy-lm`. Done and tested: `--preset big` (settings in the README), the LM text pool
(`DataPipeline.lm_pool`, `--lm-text-bytes`), per-run result files with incremental download,
`--job-dir` / `--resume` / `--prepare-only`, creation of the remote `runs/` directory before held run
files are uploaded (`colab upload` does not create directories), compressed job files, and `--gpu none`
(a CPU runtime). A full-scale `--prepare-only` ran locally and a toy-sized job ran on a Colab CPU runtime,
including an interrupted run and its resume (numbers in the README).

The full run finished on a Colab L4: 33/33 runs, `--preset big --resume --concurrency 1` at commit
`6d260c2`, resuming a job prepared at `3186c1b` from a tree with uncommitted changes
(`meta.job_prepared`; the report header says so). Results are in `benchmarks/results/colab_big/` and in the README (section 3, with the small vs
big comparison generated by `scripts/gen_readme_tables.py`).

- L4 memory (measured): `--concurrency 3` and `--concurrency 2` ran out of GPU memory on the 22 GB L4;
  `--concurrency 1` works. At concurrency 3 the processes held 9.1, 7.1 and 5.1 GiB; at concurrency 2
  one held 11.1 GiB while the other (9.1 GiB) failed to allocate 2 GiB more. The failing allocation is
  the fp32 logits of one 64 x 512 x 16,384 batch (2 GiB). The preset's default is now concurrency 1
  (`BIG_PRESET`, checked in `test_big_preset_resolves_and_flags_override`).
- Wall time (measured): 5 h 03 min from launch to the result on the laptop. Of that, the upload took
  7 min 20 s and training plus evaluation on the VM 17,699.8 s (4 h 55 min, `meta.lm_seconds`), a mean
  of 536 s (8.9 min) per run. The run files do not record per-run time. The compute units used were not
  recorded.
- Remaining idea: halve the per-run memory so 2 runs fit on one L4, with gradient accumulation (e.g.
  2 x 32 sequences per step, same 32,768 tokens per step) or a chunked cross-entropy that never holds
  the full fp32 logits. Check that BPB stays the same before using it for results.
- Concurrency vs sequential: still untested on a GPU, because the real run was sequential
  (concurrency 1). The test compares with `rel=1e-5`, not bit-equality, because separate CPU processes
  may use different thread counts. On one GPU with the same seed the runs should match; check it on the
  next run with concurrency > 1 (e.g. on an A100, or after the memory change above).
- Eval runs in fp32 (no autocast): correct, slower on the big model (eval time was not measured
  separately). If it matters, use bf16 autocast in `BpbEvaluator` with logits cast to fp32 (as training
  does) and check that BPB moves by < 0.001.
