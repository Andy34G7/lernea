Benchmarks for subword tokenisation algorithms

What is measured here

The project's subword tokenisers (BPE with different merge scores, SuperBPE, a morpheme prior, Unigram LM) are compared at four levels, from cheap to expensive. Each tab explains its benchmark; the Concepts tab explains the algorithms and metrics.

Compression & intrinsic
How much text a token covers, how evenly the vocabulary is used, and whether token boundaries match morpheme and identifier boundaries. No model is trained. V = 16,384, 32,768 and 65,536.
Throughput
Encode and decode speed, measured three times on different machines.
Proxy LM
A small Transformer trained from scratch on the same number of bytes for every tokeniser; scored in bits per byte (BPB) on held-out text. Two sizes, 3 seeds each. V = 16,384.
GPT-2 swap
GPT-2 small (124M) trained with llm.c's recipe for 600 steps, once per tokeniser, including GPT-2's own tokeniser and TokenMonster. V ≈ 50k.
FLORES+
How many more tokens the same sentences cost in 17 other languages than in English (the tokenisation premium), for the tokenisers of the intrinsic and the GPT-2-swap levels. No model is trained.

Category leaders

The best tokeniser on each headline number, the runner-up, and the run the number comes from. The benchmarks measure different things: leading one does not mean leading overall, and a small margin may be noise (see each caveat).

Six metrics, each min–max normalised to [0, 1] across all tokenisers (BPB inverted). Pick tokenisers to compare.

Measures
How compactly each tokeniser encodes held-out text in natural languages and programming languages (definitions from the vendored tokka-bench). No model is trained.
Read
Bytes/token ↑: more text per token means shorter sequences. Fertility ↓: tokens per word. Word split % ↓: words cut into two or more tokens. Continued % ↓: tokens that continue a word instead of starting one. Macro = unweighted mean over languages with enough held-out text; micro = token-weighted over all.
Caveats
  • Compression is not quality: the PMI-ranked variants and SuperBPE sit at the two extremes for reasons explained in Concepts.

  • “Words” are whitespace-separated, except Chinese and Japanese, which are counted per character.

Morph F1 by language

Per-word boundary F1 averaged within each language. The headline morph F1 is the unweighted mean over languages; word-weighted is dominated by the language with the most gold words.

Measures
Single-threaded encode and decode speed, one call per document over the held-out test split; each number is the median of 5 timed passes after 1 warm-up. Higher is better.
Three runs
Laptop suite: the intrinsic run on the shared laptop, unpinned, desktop session active, one pass. Pinned laptop core: the same tokenisers re-timed pinned to one performance core (taskset), two full passes. Colab CPU: a Colab CPU runtime whose 2 vCPUs are one core with 2 hyperthreads, two full passes. The pinned and Colab runs reload each saved tokeniser and check identical token ids before timing.
Why they differ
Different CPUs (Intel laptop vs AMD server core) and different load. The unpinned run can be scheduled on any core, including the laptop's slower efficiency cores, and competes with the desktop. The pinned run stays on one fast core. The Colab core's second hyperthread also runs the Jupyter kernel answering status polls, on a shared host.
Caveats
Compare tokenisers within one column, not across columns, and treat a difference smaller than that column's spread as noise. The README records two laptop suite runs at V = 65,536 that differed by up to 1.7× (labelled prose, not in a result file).

        The same swap with 8 of our tokenisers retrained with a GPT-2-style space_prefix pre-tokeniser: a single space attaches to the following word (“ the”) instead of being its own token. It tests whether the gap to GPT-2 comes from the whitespace tokens (less text per step) or from the merges.

        Ablation: pre-split and training text not yet run

        Per variant, the same swap with the tokeniser trained four ways: whitespace-isolating (the original run), space_prefix (the rerun above), GPT-2's exact regex pre-split (_g2), and space_prefix on 300 MB of text instead of 50 MB (_sp300). GPT-2 is the reference. It separates how text is cut before merging from how much text the merges are learned on.

        Negative result: peak lr 1.8e-3

        The same job with 3× llm.c's peak learning rate (the AdamW lr of modded-nanogpt's early records), stopped after GPT-2.

        Context (prose from the run's README): modded-nanogpt raised the lr together with architecture changes (rotary embeddings etc.); on plain llm.c GPT-2 at this 600-step budget 3× is too high.

        Measures
        The tokenisation premium: the tokens a tokeniser spends on a language's FLORES+ sentences divided by the tokens it spends on the same sentences in English. FLORES+ is professionally translated parallel text, so the content is identical. No model is trained.
        Read
        Premium ↓: 1.0 is parity with English; 2.0 means the same content costs twice the tokens (half the context, twice the price). In-mix languages are in the intrinsic tokenisers' training mix; out-of-mix languages are in no tokeniser's training text.
        Caveats
        • The premium is relative to each tokeniser's own English cost: a tokeniser that spends many tokens on English gets a low premium without being cheap on the other language. Read it next to EN tokens per sentence.
        • The GPT-2-swap tokenisers learned their merges on English text only; their premium is no fault of the merge score.
        • Bytes or characters per token are not comparable across scripts (UTF-8 spends 1 to 3 bytes per character); the premium is.

        Findings

          Concepts

          How the tokenisers work and what each metric means. Formulas and defaults are those in the README and the Rust scorers.

          Bytes & pre-tokenisation · BPE family · SuperBPE · Morpheme prior · Unigram LM · Dropout, sampling, patching · Metrics

          Byte-level tokenisation

          Every tokeniser here starts from the 256 byte values. Any UTF-8 text can be encoded and decoded back exactly, and there is no unknown token. A token is a byte string, so it can end in the middle of a multi-byte character; the playground shows such pieces as �.

          Pre-tokenisation

          Before merges are learned, text is cut into pre-tokens, and no token crosses a pre-token boundary. Our pre-tokeniser isolates every whitespace run: “the cat” becomes “the”, “ ”, “cat”. GPT-2's regex instead attaches one leading space to the following word: “the”, “ cat”. With our rule nearly every space costs a token, so on English our tokenisers cover fewer bytes per token than GPT-2 (GPT-2 swap tab). The space-prefix rerun uses GPT-2's rule; SuperBPE drops the boundary in its second stage.

          Bottom-up merges (the BPE family)

          Start from bytes. Score every adjacent pair $(u, v)$ in the training corpus, merge the best pair into a new token $uv$ everywhere, and repeat until the vocabulary has $V$ tokens. Encoding replays the merges in order. The variants differ only in the score. A pair seen fewer than min_frequency times is never merged: 2 for wordpiece_pmi, wp_bpe_ft, wp_bpe_scp, wp_bpe_npmi, wp_bpe_ppig and mdl_bits, 1 for the others.

          Frequency — bpe_frequency

          $$\mathrm{score}(u, v) = \mathrm{count}(uv)$$

          Standard byte-level BPE: merge the most frequent pair. The baseline every Δ is measured against.

          WordPiece likelihood — wordpiece_pmi

          $$\mathrm{score}(u, v) = \frac{\mathrm{count}(uv)}{(\mathrm{count}(u) + \alpha)(\mathrm{count}(v) + \alpha)}, \quad \alpha = 1,\ \mathrm{count}(uv) \ge 2$$

          Pair count over the product of Laplace-smoothed part counts. With $\alpha = 0$ and no cutoff it is exactly wp_bpe_base.

          The PMI ratio and why it degenerates — wp_bpe_base, wp_bpe_ft

          $$\mathrm{score}(u, v) = \frac{\mathrm{freq}(uv)}{\mathrm{freq}(u) \cdot \mathrm{freq}(v)}$$

          The ratio is at most $1/\max(\mathrm{freq}(u), \mathrm{freq}(v))$, and it reaches its maximum, 1, for a pair seen once whose parts occur nowhere else. So the rarest pairs are merged first. Each merge creates a rare token whose pairs are rare too, and the vocabulary fills with long strings that hardly recur in new text, which then falls back to near byte-level tokens.

          $$\mathrm{score}(u, v) = \begin{cases} \frac{\mathrm{freq}(uv)}{\mathrm{freq}(u) \cdot \mathrm{freq}(v)} & \text{if } \mathrm{freq}(uv) \ge \theta \\ -\infty & \text{otherwise} \end{cases}, \quad \theta = 2$$

          The frequency threshold $\theta = 2$ removes singleton pairs, but pairs seen twice still outrank frequent ones, and the result stays close to wordpiece_pmi.

          Pointwise information gain — wp_bpe_pig

          $$\mathrm{score}(u, v) = \mathrm{freq}(uv) \cdot \log_2 \frac{\mathrm{freq}(uv) \cdot N}{\mathrm{freq}(u) \cdot \mathrm{freq}(v)}$$

          PMI weighted by the pair's count: the total pointwise information of the pair over the corpus. A frequent, associated pair now outscores a singleton.

          Symmetric conditional probability — wp_bpe_scp

          $$\mathrm{score}(u, v) = \frac{(\mathrm{freq}(uv) - d)_+}{\sqrt{\mathrm{freq}(u)\,\mathrm{freq}(v)}}, \quad d = 0.75$$

          Geometric-mean calibrated PMI with a Kneser-Ney style discount $d = 0.75$; with $d = 0$ it is $\sqrt{P(u \mid v)\,P(v \mid u)}$. Bounded in $[0, 1)$, symmetric in $u$ and $v$.

          Normalised PMI — wp_bpe_npmi

          $$\mathrm{score}(u, v) = \mathrm{freq}(uv)^{\alpha} \cdot \frac{\ln \frac{P(uv)}{P(u)P(v)}}{-\ln P(uv)}, \quad P(x) = \frac{\mathrm{freq}(x)}{N},\ \alpha = 0.5$$

          Bouma's NPMI is bounded in $[-1, 1]$ and is $+1$ exactly when $u$ and $v$ only occur together; the support weight $\mathrm{freq}(uv)^{\alpha}$, $\alpha = 0.5$, keeps rare, perfectly associated pairs from winning outright.

          Penalised information gain — wp_bpe_ppig

          $$\mathrm{score}(u, v) = \frac{\mathrm{freq}(uv) \cdot \max(0, \mathrm{PMI}(u, v))}{(|u| + |v|)^{\eta}}, \quad \mathrm{PMI}(u, v) = \log_2 \frac{\mathrm{freq}(uv) \cdot N}{\mathrm{freq}(u) \cdot \mathrm{freq}(v)},\ \eta = 0.35$$

          Information gain counting only positive association, divided by a merged-length penalty with $\eta = 0.35$.

          Length-penalised frequency — length_penalized

          $$\mathrm{score}(u, v) = \frac{\mathrm{freq}(uv)}{(|u| + |v|)^\beta}$$

          Frequency divided by the merged length to the power $\beta = 0.5$, to slow down the growth of long tokens.

          Minimum description length — mdl_bits

          $$\Delta L = \big[L(T) - L(T')\big] - (c_{\mathrm{entry}} + 8\,|uv|), \quad L(T) = N \log_2 N - \sum_t c_t \log_2 c_t,\ c_{\mathrm{entry}} = 24$$

          Merge the pair that most shortens the corpus under a unigram code, minus the cost of the new vocabulary entry: 24 bits plus 8 bits per byte.

          SuperBPE — super_bpe

          $$\begin{cases} \text{Word-internal BPE} & |V| \le V_{\mathrm{switch}} \\ \text{Cross-word Collocations} & V_{\mathrm{switch}} < |V| \le V_{\mathrm{final}} \end{cases}$$

          Two stages. Up to $V_{\mathrm{switch}}$ it is ordinary BPE with pre-tokenisation; after that the whitespace boundary is lifted and merges may join words into “superword” tokens (“ of the”). The benchmark suite switches after 90% of the merges, $V_{\mathrm{switch}} = 256 + 0.9\,(V - 256)$ (recorded in meta.variants); the playground switches at $0.75\,V$. It gives the most bytes per token of our tokenisers.

          Morpheme prior — morpheme_bpe

          $$\mathrm{score}(u, v) = \mathrm{count}(uv) \cdot e^{\lambda M(u, v)}, \quad M = \frac{n_{\mathrm{intra}} - n_{\mathrm{cross}}}{n_{\mathrm{intra}} + n_{\mathrm{cross}}} \in [-1, 1],\ \lambda = 2.5$$

          Frequency BPE whose scores are scaled by $e^{\lambda M}$. $M$ is the share of the pair's current occurrences, in lexicon words, whose merged token stays inside one morpheme, minus the share that would span a morpheme boundary. Pairs with $\mathrm{count}(uv)\,e^{\lambda M} \lt 1$ are never merged. The formula shows the playground's $\lambda = 2.5$; the benchmark suite trains with $\lambda = 2$ and a lexicon from the SIGMORPHON 2022 train split, with every gold test word removed.

          Unigram language model — unigram_lm

          $$\mathcal{L} = \sum_{i=1}^N \log \left( \sum_{x \in \mathcal{S}(X_i)} P(x) \right)$$

          Top-down instead of bottom-up. Start from a large seed vocabulary (the most frequent substrings, found with a suffix array, about $3V$ of them) and give every token a probability. The corpus likelihood sums over all segmentations $\mathcal{S}(X_i)$ of each word.

          • EM: the E-step runs forward-backward over each word's segmentation lattice (in log space) to get expected token counts; the M-step renormalises them into probabilities. 10 EM iterations per round.
          • Pruning: drop the tokens whose removal costs the least likelihood under Viterbi segmentation, keeping a factor 0.75 of the vocabulary per round, until $V$ tokens remain.
          • Encoding: the Viterbi (most probable) segmentation.

          BPE-dropout

          $$P(\text{apply merge } (u,v)) = 1 - p$$

          While encoding LM training text, each applicable merge is skipped with probability $p$, so the model sees several segmentations of the same word. In the proxy LM, bpe_dropout_p0.1 uses the bpe_frequency vocabulary with $p = 0.1$ on training ids; validation ids are deterministic.

          Unigram sampling (subword regularisation)

          Instead of the Viterbi path, sample a segmentation from the Unigram lattice in proportion to its probability (forward-filtering backward-sampling), or among the $k$ best paths. Implemented, not benchmarked.

          Byte-entropy patching

          BLT-style dynamic patches instead of a fixed vocabulary: a back-off Markov model over bytes predicts the next byte, and a new patch starts before a byte whose predictive entropy exceeds a threshold $\tau$ bits, within a minimum and maximum patch length. Implemented, not benchmarked.

          Metrics

          Bytes per token ↑
          UTF-8 bytes of held-out text divided by the number of tokens. More bytes per token means shorter sequences: more text per context window and per training step.
          Fertility ↓
          Tokens per word (whitespace-separated; per character for Chinese and Japanese in Tokka-Bench).
          Word split % ↓
          Share of words that become two or more tokens (Tokka-Bench, on a sample of words).
          Continued-word rate ↓
          Share of tokens that continue a word instead of starting it: $\sum_w (n_w - 1) / \sum_w n_w$ over the sampled words $w$, where word $w$ has $n_w$ tokens.
          Rényi efficiency ↑
          $E_\alpha = H_\alpha(p) / \log_2 |V|$ with $H_\alpha(p) = \frac{1}{1-\alpha} \log_2 \sum_t p_t^{\alpha}$ (Shannon entropy at $\alpha = 1$), where $p$ is the token distribution on held-out text. 1 means every token is used equally often; a larger $\alpha$ penalises a few very frequent tokens more. Zouhar et al. (2023) proposed it, with $\alpha = 2.5$, as a predictor of downstream quality.
          Gini ↓, active fraction ↑
          Gini coefficient of the token frequencies on held-out text (0 = every token equally often), and the share of the vocabulary that occurs there at all.
          Morph F1 ↑
          For each SIGMORPHON 2022 gold word, the byte offsets where the tokeniser cuts it are compared with the gold morpheme boundaries: precision, recall and F1 per word, averaged per language, then over the 5 languages unweighted.
          Identifier F1 ↑
          The same on identifiers mined from held-out code. Gold cuts are at _/- runs, lower-to-upper humps (get|User), acronym ends (HTTP|Server); digits stay with the word before them. Splitting an underscore off is neither rewarded nor penalised.
          Bits per byte (BPB) ↓
          $\mathrm{BPB} = \sum_i -\ln p(t_i) \,/\, (\ln 2 \cdot B)$: the language model's total negative log-likelihood of the validation tokens, in bits, over the $B$ UTF-8 bytes of that text. Per-token perplexity cannot be compared across tokenisers: a tokeniser with longer tokens has fewer, harder predictions. BPB charges every tokeniser for the same bytes, so it is the code length the model plus tokeniser needs for the text.
          Fixed byte budget
          Proxy LM: every tokeniser's model trains on the same number of bytes of text, so a tokeniser with more bytes per token trains on fewer tokens. The GPT-2 swap fixes the other way: the same tokens per step and the same steps (the same compute), so a tokeniser with more bytes per token sees more text.
          GPT-2-equivalent steps ↑
          The first step at which GPT-2's own train BPB (its train loss in bits per byte, smoothed by a centred rolling mean) reaches a tokeniser's final val BPB: how many of GPT-2's steps buy the same quality.

          Playground

          Tokenise any text with every algorithm side by side. Hover a token to see its ID and byte length. The tokenisers here are trained on demand on 100 KB at a tiny vocabulary, not the benchmark tokenisers.
